# CMS on medicalaccountant.ie

The news is now run from an admin at `/admin`. The rest of the site (service pages, contact, terms) is unchanged and still comes from `lib/content.json`.

## What lives where

| | |
| --- | --- |
| Public pages | `app/(site)/` (all the original pages, with the site header, footer and CSS) |
| Admin | `app/(cms)/` (its own root layout and Tailwind stylesheet; nothing from it reaches the public site) |
| News list, archives | `/news/`, `/news/page/2/`, `/news/category/<slug>/`, `/news/tag/<slug>/`, `/news/author/<name>/` |
| A post | `/<slug>/`: the same WordPress-style address the posts already had, so no links or rankings change |
| How `/<slug>/` is decided | `app/(site)/[slug]/page.js`: the site's own pages (from `lib/content.json`) first, otherwise a CMS post |
| Sitemap, feed, robots | generated by the CMS: `/sitemap.xml`, `/feed.xml`, `/robots.txt` (the old `sitemap.js` and `robots.js` were replaced) |
| Design of the news | `components/blog/ArchiveCard.tsx`, `ArchiveView.tsx`, `PostPage.tsx`, `app/css/blog-cms.css` (they reuse the site's `PostCard`, hero and contact panel) |
| Home page "Latest news" | `lib/latest.ts`: newest CMS posts, falling back to `lib/content.json` if the database is empty |

The site's own pages (home, contact, terms and the seven audience pages) are still listed by hand in `app/sitemap.ts`. Add a line there when you add a page.

## Set up (one time): Cloudflare Workers

The site runs on one Cloudflare Worker (Next.js through OpenNext), with a **D1** database and **R2** buckets. Everything is declared in `wrangler.jsonc`.

1. **Log in.** `npx wrangler login`.
2. **Database.** `npx wrangler d1 create medical-accountant-db`, paste the printed `database_id` into **both** `d1_databases` entries in `wrangler.jsonc`, then `npm run db:migrate:remote` (creates the tables from `migrations/`). Optionally `npx wrangler d1 execute DB --remote --file database/import-existing-posts.sql` (the seven original posts).
3. **Buckets.** `npx wrangler r2 bucket create medical-accountant-uploads` (uploads, served by the site at `/files/<bucket>/<name>`) and `npx wrangler r2 bucket create medical-accountant-opennext-cache` (page cache).
4. **Secrets.** For each name in `.dev.vars.example` run `npx wrangler secret put NAME`: `ADMIN_EMAIL`, `ADMIN_PASSWORD` (8+ characters, longer is better), `POSTS_API_KEY`, `REVALIDATION_SECRET`, `INDEXNOW_KEY`. The first sign-in at `/admin/login` creates the admin account; changing `ADMIN_EMAIL` or `ADMIN_PASSWORD` later changes the login. No SQL needed.
5. **Email.** Form emails go through Cloudflare Email Sending (the `send_email` binding `EMAIL` in `wrangler.jsonc`). In the dashboard: Compute > Email Service > Email Sending > Onboard Domain, and pick the domain of `EMAIL_FROM` (`medicalaccountant.ie`); Cloudflare adds the DNS records. `ADMIN_NOTIFICATION_EMAIL` (a var in `wrangler.jsonc`) is where enquiries go. On Workers Paid any recipient works; on the free plan only addresses verified under Email Routing > Destination Addresses.
6. **Deploy.** `npm run deploy` (builds, then uploads the Worker). Add the domain under Workers & Pages > medical-accountant > Settings > Domains & Routes.
7. **Automatic deploys.** Cloudflare Workers Builds (the Git connection under Workers & Pages > medical-accountant > Settings > Builds) deploys every push to `main`. Set its **Build command** to `npm run cf:build` (runs the tests, then builds) and its **Deploy command** to `npm run cf:deploy` (applies D1 migrations, then deploys). The build's API token needs D1 edit permission for the migrations.

`NEXT_PUBLIC_*` values (site URL, tracking ids) are baked in at build time. `NEXT_PUBLIC_SITE_URL` comes from the `vars` in `wrangler.jsonc` for both the build and the running Worker (a build variable of the same name in the Workers Builds settings overrides it). Any other `NEXT_PUBLIC_*` value goes under **Build variables** in the Workers Builds settings.

The Worker bundle is about 3.6 MB gzipped, so it needs the **Workers Paid** plan (the free plan's limit is 3 MB).

### Moving data from the old Supabase/Vercel site

Both scripts only read from Supabase (they need the old `DATABASE_URL`, `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` in `.env.local`; `DATABASE_URL` must be the **Transaction pooler** string):

1. `node --env-file=.env.local scripts/export-supabase.mjs` writes `.migration/d1-data.sql`; load it with `npx wrangler d1 execute DB --remote --file .migration/d1-data.sql`.
2. `node --env-file=.env.local scripts/export-storage.mjs --remote` copies the uploaded files into the R2 bucket, keeping the same `/files/...` URLs.
3. Check the site on its `*.workers.dev` address, then point the domain at the Worker. Once it is live, delete both scripts and the `pg` and `@supabase/supabase-js` dev dependencies.

## Day to day

- **Write or edit a post:** Admin > Posts. The seven original posts are already there, with their SEO titles, images and dates.
- **Locally:** copy `.dev.vars.example` to `.dev.vars` and fill it in, run `npm run db:migrate` once (a local D1 in `.wrangler/`), then `npm run dev`. `npm run preview` runs the real Worker build locally.
- **A post's address** is its slug, directly under the site root. Slugs the site already uses (`news`, `contact`, `terms`, `gp-accountants`, `ihca`, ...) and the CMS routes (`admin`, `api`, `page`, `tag`, `category`, `author`) get `-post` added.
- After the import, the posts in `lib/content.json` are no longer used for the news pages. Edit them in the admin; the JSON copy is only the fallback for the home page's "Latest news" when the database is empty.

## Not switched on (the site had none of it before)

The CMS can add analytics scripts and a cookie banner from Admin > Site Settings. They are **not** loaded on the public pages, because the banner is styled with Tailwind and the public site does not use it.

## Enquiries

The enquiry form (home, service pages, blog posts and `/contact`) submits to `/api/forms/submit` as the built-in **Website enquiry** form (slug `enquiry`, created on the first submission). Each enquiry is saved under Admin > Forms, emailed to the form's recipient (Reply-To is the visitor) and, with the visitor copy switched on, emailed to the visitor. Recipient, subjects, templates and the visitor copy are edited in Admin > Forms. The dropdown options live in `lib/forms/enquiry-options.ts`; if you change them in the admin, change that file to match, or the server will reject the old options.
